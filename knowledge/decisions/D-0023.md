# D-0023: Explicit bag deposits, consistent mount rejection and vanilla HUD frames

Date: 2026-09-18. Status: Active. Supersedes the ordinary-storage fallback in
the original implementation direction; D-0008's independent Quick Slot and
direct mount exchange remain in force.

Rusty reported that releasing G over an incompatible occupied mount put the
held item inside the backpack. Native G/wheel input reproduced both directions:
apples against a long mount and an axe against a small mount. Empty mounts
already refused, making the same gesture depend unexpectedly on occupancy.

Rusty proposed a separate scrollable backpack icon with an arrow and a "put in
bag" label, then chose "Add both held-item and direct mount stowing". They also
requested that Quick Slot and mount HUD cells look like the normal hotbar.

The accepted interaction is:

- Incompatible mount exchanges leave every item untouched. A red vanilla
  selection frame and slot-size explanation make the refusal visible.
- Holding G adds a bag action beside each occupied mount, and another for a
  nonempty held stack. Arrows identify the mounted source; labels distinguish
  "Put mounted [item] in bag" from "Put held [item] in bag".
- Wheel order visits each mount, then its storage action. Held-item storage is
  last. Release G commits the highlighted action only after scrolling.
- Deposits move the entire stack into ordinary storage, preserving components.
  Partial capacity refuses the whole move. A direct mount deposit never moves
  the held stack or another mount. Portable-storage admission is unchanged.
- The choice list and capacity previews are frozen for one gesture; bag,
  hotbar or held-stack changes, focus loss and menus cancel it.
- Both mods use the active resource pack's vanilla hotbar/selection sprites.
  The persistent mount row remains horizontal, with compact and mirrored
  layouts retaining vanilla status/offhand/attack-indicator clearance.

Backpacks+ protocol 4 adds an explicit storage intent and a distinct STORE
semantic action. Clients send identity, revision and source indices, never item
data. The server validates its equipped bag and actual stacks and commits once.
STORE does not masquerade as a hand/mount exchange animation. Both endpoints
must update together; Quick Slot's protocol and stored data do not change.

Validation covers real-server atomic transfers, pure immutable choice order,
and native G/wheel/release in a shader-enabled client. A client-only visual gate
is necessary because headless GameTests cannot judge HUD sprites or placement.
Implementation is authorized. Publication, pack updates and deployment are held
until a separate release go. Client delivery will be through Mod Hub; Rusty
updates Prism themselves.
